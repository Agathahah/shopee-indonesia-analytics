# Shopee Indonesia Seller Analytics

**One Shopee seller, 20,848 orders, December 2023 – November 2025.** 56% of completed revenue comes from three provinces, COD is used for 55% of orders, and 88 buyer locations generate 71% of revenue.

SQL-first analytics on a public seller export: Python loads the data into PostgreSQL, seven SQL files and eight views do the analysis, and Tableau Public / Looker Studio show the results.

## Unit of analysis: buyer locations, not customers

The seller export has **no buyer identifier**. The pipeline therefore groups orders by city/regency + province. The `customers` table keeps its name for compatibility, but each of its 424 rows is a location. RFM segments, "churn" and "champions" below describe locations, not individual people. Reading them as customers would overstate what the data can say.

## Key findings

All numbers come from [`data/insights/key_metrics.md`](data/insights/key_metrics.md), generated by `scripts/export_all.py`.

**Revenue is concentrated in western Java.** Completed revenue is Rp 1.05 billion. Jawa Barat (26.3%), Banten (16.9%) and DKI Jakarta (12.9%) together account for 56.2%. The top ten provinces account for 86.4%.

**COD dominates order count but not revenue.** 55.3% of all orders are paid by COD, but COD orders bring 38.5% of completed revenue: COD orders are smaller on average. Shifting buyers to digital payment is therefore mostly about cancellations and cash handling, not about revenue size.

**A few locations carry the business.** 88 of 409 buyer locations with completed orders (21.5%) are "Champions" and generate 71.4% of revenue. 121 locations (29.6%) are "Hibernating" or "Lost" and generate 2.9%.

**Cancellations:** 2,830 of 20,848 orders (13.6%) were cancelled.

## Recommendations

| Priority | Recommendation | Why |
|---|---|---|
| High | Protect delivery quality in Jawa Barat, Banten and DKI Jakarta | 56% of revenue; a courier problem there hits the whole business |
| Medium | Test a small cashless incentive and measure cancellation rate by payment method | COD is 55% of orders; the effect on cancellations must be measured, not assumed |
| Medium | Test location-targeted promotions in "At Risk" locations (35 locations, 6.6% of revenue) | Cheaper to keep active areas than to reactivate dormant ones |

These are hypotheses for experiments. The data cannot show causal effects.

## Audit, October 2026: what changed and why

| # | Problem in v1 | Impact | Fix |
|---|---|---|---|
| 1 | **COD filter matched nothing.** `sql/05` compared `payment_method = 'COD'`, but the raw value is `'COD (Bayar di Tempat)'`. The Tableau CSV also labelled COD orders as `Digital`. | COD vs digital comparison and the "COD 38% of transactions" claim were wrong. COD is 55.3% of orders; 38.5% is its share of revenue. | `ILIKE 'COD%'`, new order-level view `vw_dashboard_orders`. |
| 2 | **1,980 orders (9.5%) silently dropped.** Two monthly files (December 2024, July 2025) have no timestamps; the loader skipped those rows without logging. | Revenue understated by about Rp 98 million; December 2024 and July 2025 looked like slumps. | Orders kept, dated to the first day of the month in the file name, flagged with `timestamp_is_estimated`. Loader now records any rejected row with a reason. |
| 3 | **Locations presented as customers.** `customer_id` = hash of city + province, and Faker generated names and phone numbers for each location. | "117 customers churned" was 117 locations. Fake names made locations look like people. | Faker removed; README and schema say "buyer location". |
| 4 | **Hand-written metrics file.** `data/insights/key_metrics.md` contained figures that do not match the data (e.g. Banten 7.2% instead of 16.9%, Jawa Tengah ranked 2nd instead of 4th). | Anyone quoting it would be wrong. | File is generated from SQL by `scripts/export_all.py`. |
| 5 | **README SQL snippet differed from the real query** (it used `CURRENT_DATE` and ranked recency in the wrong direction). | Misleading for readers checking the logic. | Snippet removed; see `sql/03_rfm_segmentation.sql` and `sql/07_views_dashboard_prep.sql`. |
| 6 | **Database password committed** in three scripts. | Credential in a public repo. | Read from environment variables (`.env.example`). |
| 7 | **`requirements.txt` was a 120-line `pip freeze`** including Jupyter. | Slow, fragile installs. | Four direct dependencies. |
| 8 | **Results depended on row order and database locale.** RFM scores used `NTILE(4)` over columns with many ties, so which tied location landed in which quartile was arbitrary; exports sorted text by the database collation and left ties unordered. A re-run on another laptop reordered rows, and a different tie order can move locations between segments (here: Loyal 58 → 56, At Risk 33 → 35). | Segment counts were not strictly reproducible; every re-run produced git diffs. | `customer_id` as tie-breaker inside `NTILE`, explicit tie-breakers in every final `ORDER BY`, the database created with `--locale=C`. Shuffling the input file now gives byte-identical exports. |

## Pipeline

```
Kaggle CSV (20,848 rows, 19 columns)
   │  scripts/ingest.py: normalise, flag estimated timestamps, log rejects
   ▼
PostgreSQL 16: customers (= locations, 424), products (679), shipping_methods (45), orders (20,848), payments (20,848)
   │  sql/01–06: data quality, revenue trend, RFM, shipping, payment, category
   │  sql/07: 8 dashboard views
   ▼
scripts/export_all.py ──► data/exports/*.csv, data/insights/key_metrics.md
scripts/export_tableau_csv.py ──► data/tableau/   ──► Tableau Public
scripts/prepare_for_sheets.py ──► data/sheets/    ──► Looker Studio
```

## How to run

```bash
git clone https://github.com/Agathahah/shopee-indonesia-analytics.git
cd shopee-indonesia-analytics
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# PostgreSQL (macOS example)
brew install postgresql@16 && brew services start postgresql@16
cp .env.example .env && set -a && source .env && set +a   # edit PGUSER/PGPASSWORD first
# C locale: text sorts the same on every machine, so exports are byte-identical
createdb -T template0 --locale=C -O "$PGUSER" nusacommerce   # run as a superuser (e.g. -U $(whoami))
psql -d nusacommerce -f sql/01_schema.sql

# Data
kaggle datasets download -d bakitacos/indonesia-e-commerce-sales-and-shipping-20232025 --path data/raw/ --unzip

# Pipeline
python scripts/ingest.py              # prints rows loaded and rows rejected (with reasons)
python scripts/export_all.py          # runs all SQL, writes exports + key_metrics.md
python scripts/export_tableau_csv.py
python scripts/prepare_for_sheets.py
```

## Limitations

- Single seller, so findings describe this shop, not Shopee Indonesia as a whole.
- No buyer ID: no customer-level retention or lifetime value.
- November 2025 may be incomplete in the export; month-over-month changes for the last month should be read with care.
- Orders with estimated timestamps (1,980) use the first day of their month, which slightly shifts recency for those locations.

## Dataset

[Indonesia E-Commerce Sales & Shipping 2023–2025](https://www.kaggle.com/datasets/bakitacos/indonesia-e-commerce-sales-and-shipping-20232025) (Kaggle, bakitacos): seller export, semicolon-separated, Indonesian column names.
